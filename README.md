# DevDock

基于 Tauri 2、Vue 3 和 Rust 的本地开发工作台。支持 macOS，并加入 Windows 基础工作台适配：管理 uni-app、Node.js 项目、运行终端命令、Git 分支展示及 JSON 备份。App 构建与 HBuilderX 菜单自动化目前仅支持 macOS。

## 启动

需要 Node.js 22+、pnpm 11、Rust 1.89+。macOS 需要 Xcode Command Line Tools；Windows 需要 MSVC C++ Build Tools、Windows SDK 与 WebView2。

```sh
pnpm install
pnpm tauri dev
```

仅预览界面可运行 `pnpm dev`。浏览器预览使用独立 localStorage，不读写桌面应用配置，不执行本地构建和终端命令。

```sh
pnpm build                       # 类型检查与前端生产构建
pnpm test                        # 配置合并测试
cargo test --manifest-path src-tauri/Cargo.toml
bash scripts/test-hbuilderx.sh    # macOS：WGT 匹配和菜单占位项，不触发打包
bash scripts/test-hbuilderx.sh --live-menus # 只读检查当前 HBuilderX 菜单，不点击运行/发行
bash scripts/test-terminal.sh     # macOS：长命令分块切分，不打开终端
bash scripts/test-build.sh        # macOS：伪 JDK/Gradle 验证兼容参数与资源复制
pnpm tauri build                 # 构建本机架构的 macOS 应用与 DMG
```

macOS 构建结果位于 `src-tauri/target/release/bundle/`。对外分发前需自行配置 Apple Developer 签名与公证。Windows 安装包需要在 Windows 构建和验证，步骤见下方。Windows 支持基础工作台及终端执行，HBuilderX 菜单自动化和 APK/WGT 构建入口暂不可执行。

## 版本管理与 Release 发布

`.github/workflows/release.yml` 的 **Release Draft** 工作流负责准备发布：推送 `v版本号` Tag 后，先校验版本，再并行构建 Windows x64 EXE 和 macOS 通用版 DMG；两边都成功且 SHA256 校验通过后，将原始文件上传至 GitHub Release 草稿，**不会自动公开**。维护者在 **Releases** 检查草稿的 Assets 后，手动点击 **Publish release**。公开后用户可直接下载 `.exe` / `.dmg`，无需解压 Artifacts ZIP。

发布版本是 DevDock 自身版本，与业务项目的 APK/WGT 版本无关。同步工具同时维护以下四处，只替换应用版本，不更新依赖：

- `package.json` 的 `version`。
- `src-tauri/tauri.conf.json` 的 `version`。
- `src-tauri/Cargo.toml` 的 `[package].version`。
- `src-tauri/Cargo.lock` 中 `dev-dock` 根包版本。

例如准备发布 `0.2.0`：

```sh
pnpm version:set 0.2.0
pnpm version:check
git add package.json src-tauri/tauri.conf.json src-tauri/Cargo.toml src-tauri/Cargo.lock
git commit -m "chore(release): 发布 0.2.0"
git tag v0.2.0
```

确认提交与 Tag 后，手动推送到 GitHub。以下示例使用本地已配置的 `github` 远程名，其他克隆需替换为实际 GitHub 远程名（通常为 `origin`）：

```sh
git push github master
git push github v0.2.0
```

推送 Tag 后，在 GitHub 完成以下步骤：

1. 打开 **Actions → Release Draft**，查看该 Tag 对应的运行记录。仅推送 `master` 不会触发此工作流。
2. 等待版本校验、Windows 和 macOS 构建、草稿附件上传全部成功；任一平台失败时，不会继续上传草稿附件。
3. 打开仓库 **Releases**，找到对应版本的 **Draft**，进入编辑页面。草稿尚未发布，普通下载者看不到此版本。
4. 检查版本、发布说明，以及 **Assets** 中的 `.exe`、`.dmg` 和各自的 `.sha256` 文件，确认后点击 **Publish release**。
5. 发布后，从该版本的 **Assets** 下载安装包。GitHub 自动生成的 **Source code (zip/tar.gz)** 是源码，不是安装包；**Actions → Artifacts** 下载的仍是 ZIP。

如果构建或上传失败，在对应 Actions 运行页面查看失败步骤；临时失败可用 **Re-run failed jobs** 重试。需要修改源码时，修复并验证后使用新的版本提交与 Tag，避免移动旧 Tag。整个流程无需在本机提前生成 EXE 或 DMG。

版本必须一致：Tag 为 `v0.2.0`，项目四处版本都应是 `0.2.0`；不匹配时在构建前失败。工具支持 `0.2.0-beta.1` 等预发布版本，Release 自动标记为预发布；不支持 build metadata。应用右上角版本同样读取 `package.json`，不再写死。

发布工作流仅草稿上传步骤申请仓库内容写权限，使用 GitHub 自动提供的 `GITHUB_TOKEN`，无需个人访问令牌。已公开的同版本 Release 会拒绝覆盖；上传失败留下的草稿可通过重跑失败任务继续补齐附件，最终公开始终由维护者手动完成。修复源代码需要新的版本提交和 Tag，不应强制移动已发布 Tag。

`pnpm test:version` 验证同步与标签校验，`pnpm test:release` 使用 CLI 替身验证发布保护，不会访问 GitHub 或创建真实 Release。两个独立手动打包工作流继续提供 Artifacts ZIP，适合验证构建；要直接下载安装包，应使用本节的 Tag 发布流程。

## 应用内更新

安装版 DevDock 启动时检查一次更新，之后每 4 小时检查一次；点击右上角版本号可手动检查。仅检查 GitHub 最新的正式 Release，草稿和预发布版本不会进入默认更新通道。浏览器预览和开发模式不执行真实更新。

发现新版本后，版本号旁显示「更新」。点击后下载当前系统对应的更新包并展示进度；下载和签名校验全部成功后，提示下载完成并显示「重启更新」。此时不会自动安装，用户点击后才安装并重启。下载或安装失败可重试，不把下载 100% 当作校验成功。下载中、等待重启及安装中暂停定时检查；DevDock 仍有任务执行时禁止安装，需等待任务完成。重启前请保存尚未提交的配置。已下载的更新保留在当前进程内存中，退出应用后需重新下载。

更新清单来自 `https://github.com/aixiaodoucn/devDock/releases/latest/download/latest.json`，由 Release Draft 工作流生成。Windows x64 使用签名的 NSIS EXE，macOS 两种架构共用签名的 Universal `DevDock.app.tar.gz`；DMG 继续供用户手动安装。更新器验证固定公钥和签名中的版本，校验失败不会安装。更新签名免费，但不代替 Apple Developer ID、公证或 Windows Authenticode，也不会免除 macOS 辅助功能和自动化授权。

### 首次配置更新签名

两个打包工作流现在都需要更新签名私钥；缺少时会在构建前明确失败。维护者应在仓库 **Settings → Secrets and variables → Actions → New repository secret** 配置：

| Secret                               | 内容                                                                          |
| ------------------------------------ | ----------------------------------------------------------------------------- |
| `TAURI_SIGNING_PRIVATE_KEY`          | 与 `src-tauri/tauri.conf.json` 中公钥匹配的私钥文件完整内容，不是本机文件路径 |
| `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | 私钥密码；无密码私钥可不设置                                                  |

私钥只能保存在维护者本机和 GitHub Secret 中，不得提交、放入 Release 附件或替换为公开的测试密钥。配置的公钥属于发布线的固定身份，后续版本必须继续使用匹配的私钥；丢失私钥后不能直接换一套密钥为既有客户端更新。需要独立维护新的发布线时，可用 `pnpm exec tauri signer generate --ci -w ~/.tauri/devdock-updater.key` 生成密钥，并将 `.pub` 文件内容配置为公钥，妥善备份私钥；已有发布线不要重新生成或覆盖。

本机构建同样需要提供签名环境变量，例如私钥保存在上述路径时：

```sh
TAURI_SIGNING_PRIVATE_KEY="$HOME/.tauri/devdock-updater.key" \
TAURI_SIGNING_PRIVATE_KEY_PASSWORD='' \
pnpm exec tauri build
```

### 发布可更新版本

1. 配置上述 Secret，按版本管理流程同步版本、提交并推送新的 Tag。
2. 等待两平台工作流生成安装包和 `.sig`；Release 工作流验证产物并生成 `latest.json`，一起上传至草稿。
3. 检查草稿中包含 EXE、DMG、SHA256、`DevDock.app.tar.gz`、两个更新包的 `.sig` 以及 `latest.json`，再手动 **Publish release**。草稿不会被客户端发现。
4. 首个带更新功能的版本需要手动安装一次；之后安装版客户端会按上述间隔检查更高版本。macOS 应先将应用安装至可写的应用目录，不要直接从只读 DMG 运行并尝试更新。

开发验证：`pnpm test:release` 覆盖草稿发布与更新清单生成，原生更新测试覆盖真实签名校验、签名版本不匹配拒绝安装及任务互斥。测试使用合成数据，不下载安装真实 Release 或覆盖已安装应用。

## macOS 通用版打包

`.github/workflows/macos-installer.yml` 提供手动触发的 **macOS Installer** 工作流，使用 `macos-latest` runner，生成同时支持 Intel 和 Apple Silicon 的 Universal `.dmg` 安装包。

1. 将 workflow 和代码更新到 GitHub 默认分支（本项目使用 `master`）。
2. 在 **Actions → macOS Installer → Run workflow** 中选择要构建的分支并运行。
3. 成功后在运行详情底部 **Artifacts** 下载 `DevDock-macos-universal-运行编号`。
4. 解压 ZIP，`dmg/` 中为 `.dmg` 和 `.dmg.sha256`，`macos/` 中为 app 更新包及 `.sig`；DMG 中包含 `DevDock.app`。产物保留 7 天。

工作流安装锁定版本依赖，配置两个架构的 Rust 标准库，运行前后端测试及纯脚本测试，然后以 `universal-apple-darwin` 目标构建 DMG。安装包使用 ad-hoc 签名，无需 Apple Developer 证书；更新包另需配置上节的更新签名 Secret。它不包含 Developer ID 签名和 Apple 公证，macOS 可能提示开发者未验证，正式分发仍需另外配置签名与公证。

仅上传安装包和校验文件，不创建 Release，也不向仓库提交或推送。配置检查不代表 GitHub 构建已经成功，实际结果以 Actions 运行日志和安装验收为准。

## Windows 基础版与打包

第一阶段已加入 Windows 平台实现，但当前开发机器为 macOS，Windows 目标编译、真实终端和安装包行为仍需在 Windows 实机验收；macOS 测试不能替代这一步。

- 项目管理、排序、Git 分支、读取 package.json、自定义终端命令、逐命令环境变量、JSON 导入导出可使用基础工作台逻辑。
- 支持盘符和 UNC 路径，Windows 路径去重忽略大小写并统一分隔符；Mac 路径仍区分大小写。跨系统备份可导入，执行前需重新配置本机实际目录、终端和 Node 安装位置。
- 默认终端为 PowerShell，也可在偏好设置检测 Windows Terminal / PowerShell 7 或手动选择 `wt.exe`、`powershell.exe`、`pwsh.exe`。在 Windows 上使用 Mac `.app` 终端路径会提示重新选择。
- 终端通过普通启动参数读取当前用户数据目录中的一次性 JSON，再删除该数据文件。目录、环境变量、命令内容按数据交接，无剪贴板模拟；目录切换失败时不继续执行命令。启动错误显示在保留的终端中，不修改执行策略、不提权。
- Windows 命令遵循 PowerShell 语法，Mac 专用命令需要自行调整。读取 package.json 后提供 `npm.cmd` / `pnpm.cmd` / `yarn.cmd` 建议，使用工具官方 Windows 入口；手填命令若遇到 `npm.ps1` 策略限制，也可使用 `npm.cmd run dev`，应用不尝试绕过组织策略。
- 检测 nvm-windows 的已安装版本；所选 `node.exe` 目录只加入新会话的 PATH，不执行 `nvm use`，不改变全局链接。版本不存在时在交接前失败，不自动下载或换版本。
- 托盘采用彩色图标，关闭主窗口后可从托盘恢复。受管理的任务进程采用 Windows Job Object 取消进程树；交给外部终端的长期会话由用户在终端中停止。
- HBuilderX 安装路径和 JDK 可检测、保存，但 HBuilderX 菜单读取/执行、停止小程序及 App 构建暂不支持。读取 uni-app.scripts 仍可用于配置、迁移操作。

在 **Windows x64** 电脑中准备 Node.js、pnpm、Rust MSVC 工具链、Visual Studio C++ Build Tools（含 Windows SDK），确认项目依赖已安装，然后运行：

```bat
scripts\build-windows.cmd
```

脚本检查工具与依赖，运行前后端测试后生成 NSIS `.exe`，不自动安装项目依赖。若尚未安装依赖，先确认并手动执行 `pnpm install --frozen-lockfile`。安装包输出目录：

```text
src-tauri\target\x86_64-pc-windows-msvc\release\bundle\nsis\
```

安装默认仅针对当前用户，提供简体中文/英文。WebView2 已安装时沿用本机版本，否则安装器下载引导程序；首次打包也可能需要联网下载 Tauri 的 Windows 打包工具。正式发布仍需在 Windows 检查签名、升级、卸载与数据保留。

实机验收至少覆盖：中文/空格/单引号目录，长 JSON 环境变量的 Node 读取，所选 Node 版本与原终端默认版本相互独立，托盘打开/关闭和多屏缩放，项目拖拽排序、文件定位，以及安装/升级/卸载。Windows 专属文件占用与 Job 测试由上述 Windows 构建脚本执行。

### 使用 GitHub Actions 打包 EXE

仓库提供 `.github/workflows/windows-installer.yml`，在 GitHub 的 `windows-latest` runner 上构建 **Windows x64 NSIS 安装包**，可手动运行或由 Release Draft 调用。无需 Windows 代码签名证书，但需配置上节的更新签名 Secret；生成的安装包尚无 Authenticode 发布者签名。

1. 将源码和 workflow 提交到 GitHub 仓库的默认分支。若仓库将公开，请先完成历史隐私检查；也可先在私有仓库构建。
2. 打开 GitHub 仓库的 **Actions → Windows Installer**。首次使用可能需要启用 Actions。
3. 点击 **Run workflow**，选择要构建的分支并运行。手动入口只有在 workflow 已存在于默认分支后才会显示。
4. 等任务成功，进入本次运行详情，在底部 **Artifacts** 下载 `DevDock-windows-x64-运行编号`。
5. 解压下载的 ZIP，里面的 `.exe` 是安装包，旁边 `.exe.sha256` 是校验文件，`.exe.sig` 用于应用内更新签名验证。产物保留 7 天，可在过期前下载保存。

工作流自动配置 Node.js、项目指定版本的 pnpm 和 Rust MSVC，安装锁文件中的依赖，再调用现有 `scripts/build-windows.cmd` 完成前后端测试与打包。Action 版本固定到已核实的提交，仓库权限仅为读取；上传范围仅安装包、更新签名与校验文件，不上传配置、备份或整个 target 目录。工作流不创建 Release、不提交或推送代码。

若运行失败，查看第一个失败步骤的日志；测试失败时不会继续生成安装包。当前 Windows 适配仍需真实 runner 编译与实机验收，工作流文件本身不代表已经构建成功。未签名安装包可能显示 Windows 未知发布者提示，正式分发可另外配置代码签名。

## 配置项目

左侧添加项目，选择本地目录、类型与支持的平台：

- **uni-app**：App、Web、小程序。
- **Node.js**：Web、小程序。
- **backend**：父目录及多个子项目管理、SCM 分支映射、批量 Git 切换与测试分支合并，不启动后端业务服务。

平台表示操作用途分类：微信、钉钉、支付宝、百度、抖音等统一归入「小程序」，具体目标由操作名称、菜单路径或终端命令区分。旧配置中的 `pc` 自动转为 `web`，`weixin` / `dingtalk` 合并为 `miniapp`，保留原有全部操作与菜单路径；旧 JSON 备份同样兼容，保存和导出使用新分类。

编辑、移除仅影响工作台配置；移除不会删除本地源码。可以从 `package.json` 读取 scripts，选择添加为终端操作。命令、项目目录和菜单路径均保存在本机。

左侧项目列表可以拖拽调整顺序，松手后保存到配置，菜单栏快捷弹框同步使用该顺序；拖动到列表外取消时恢复原顺序。

uni-app、Node.js 项目标题旁以主题色标识显示当前 Git 分支，进入项目或窗口重新获得焦点时刷新。仅本地只读查询，支持尚无提交的分支和 worktree；非 Git 目录显示「非 Git 仓库」，detached HEAD 显示「游离 HEAD」。长分支名自适应宽度并自动换行，悬停也可查看完整名称；读取失败可悬停查看原因。浏览器预览不读取本地仓库。

## 后端项目组与 SCM

1. 新建或编辑后端项目，设置父目录。编辑器自动只读扫描直属子目录，自动过滤以点开头的文件夹，Git 仓库默认勾选，普通目录默认不选；名称与目录同行显示，勾选后点击「保存项目」即添加，无需额外确认按钮。重复扫描不会覆盖已配置的名称和映射，切换父目录也不会自动删除已有子项目。
2. 编辑项目时只维护子项目名称和目录，无需填写 SCM 信息；已有映射会保留。开发和测试分支从 SCM 自动填入并只读展示，无需手动修改或保存；标签与对应内容同行，开发和测试各占一行，使用等宽字体并提供完整悬浮名称；当前分支与预检计划中的长分支名支持换行；本地分支与 SCM 开发分支不同时标记「尚未切换」，未读取到本地状态时不作该判断。仓库 Git remote 默认 `origin`，与 SCM Git ID 一起在标题旁只读展示；同一真实仓库不能在同一个批次重复操作。普通目录可以作为目录记录保存，不适用于 Git 操作。
3. 在后端工作台输入 SCM 的 HTTPS 根地址、账号和密码登录。会话仅由 Rust 后端维护；勾选「记住登录」才通过 macOS 钥匙串／Windows 凭据管理器保存会话，不保存密码。普通配置、JSON 备份和前端状态不包含 Cookie。退出登录只清理本机连接，不退出其他浏览器会话。
4. 填写开发 SCM 项目 ID（或项目链接）后点击「加载模块」，自动按明确 Git ID 或唯一仓库地址匹配本地子项目，将开发 SCM 分支填入开发分支并保存映射。测试 SCM 项目 ID 可选：填写后将同 Git ID 的测试 SCM 分支填入测试分支；未填写不请求测试模块，也不清空原测试目标。明确选择的测试项目中缺少对应仓库时，该行测试目标会清空并提示，避免误合并到旧分支。匹配不明确时需核对本地目录及其 Git 远端地址，不按目录名猜测。
5. 「SCM 项目与仓库」将 SCM 来源配置和本地仓库合并展示，每个关联仓库只显示一次，集中显示目录、Remote、Git ID、开发/测试/本地当前分支及操作入口。未匹配本地目录的开发 SCM 模块也会列出，提供「关联本地目录」入口，不可勾选执行；测试 SCM 独有模块不展示。未加载时显示已配置总数和加载提示。其他本地目录仍保留在项目配置中，可通过「编辑项目 / 扫描父目录」维护，不会因筛选删除。开发 ID 改变后需重新加载对应范围。
6. 「切换开发分支」在当前开发来源已加载、匹配和保存成功，至少勾选一个可见仓库，远端及开发分支完整、工作区状态正常且干净、没有加载/保存/执行任务时可点击。不需要测试项目 ID。按钮旁显示具体禁用原因；点击后先获取远端并预检，核对计划后确认才真正切换。「合并到测试分支」还要求所选仓库有明确且不同的测试目标。修改 SCM 项目 ID 后重新加载模块即可同步并自动保存，无单独的「保存映射」按钮；自动保存失败会保留已读取内容，重新加载模块可重试，未保存成功时禁止执行 Git 操作。

有效会话在进程内复用，已记住的 Cookie 未变化时不重复读写系统凭据；恢复后的会话也使用相同去重规则。Cookie 变化才更新一次，存储失败保留当前内存登录并提示，不随每次查询自动重试授权；登录失败不再先删除旧凭据。首次保存或新进程从系统恢复记住的登录时，是否需要授权仍由 macOS／Windows 决定，不能绕过系统权限。

SCM 适配目前使用普通表单登录与 HTML 读取：`/kpi/loginSmt`、`/kpi/project/list`、`/kpi/project/project?show_type=2&id=...`、`/kpi/gitmode/list`。仅接受 HTTPS 根地址，重定向不得离开同一站点；登录页返回 200 也会识别为会话失效。没有假设 OAuth、refresh-token 或任意测试分支合并接口。页面结构不匹配会明确报错，不返回猜测分支。SCM 认证与本机 Git 的 SSH／凭据认证分别处理。

### 批量 Git 与冲突处理

- 切换只使用已存在本地分支或明确的远端跟踪分支，不丢弃修改，不自动 stash、提交、reset 或 clean。本地测试分支仅领先远端时保留已有提交，并在计划中提示推送将包含这些提交；落后或分叉时需先同步整理，不覆盖本地提交。
- 合并只包含当前已提交的开发代码，并校验来源与所配置开发分支一致。在独立 worktree 合并到测试分支，原目录继续停留在开发分支；不调用 SCM 页面中指向 trunk 的合并按钮。
- 「pom.xml 冲突时保留测试分支版本」默认关闭。未勾选时，遇到合并冲突会保留工作区并提示手工处理；勾选后，仅对冲突的 `pom.xml`（含子模块同名文件）采用测试分支版本，测试侧已删除的文件继续删除。其他代码冲突仍需手工处理，无冲突的 pom 变更正常合并；只有全部冲突解决后才按原有钩子与签名规则提交，不使用整仓库 ours 策略。策略会显示在确认计划中，修改选项后需重新预检。
- 沿用仓库的钩子、提交签名和 SSH 配置，不为后台操作关闭这些规则。后台不弹交互认证，需先准备本机 SSH／签名代理；仓库规则拒绝合并时保留工作区处理。
- 默认不推送；只有明确勾选「合并成功后推送测试分支」并确认计划后，才执行对应测试分支的普通推送，不使用强制推送。
- 批次顺序执行，遇错暂停，已成功的仓库保留结果；跨仓库不是原子事务，不承诺全部回滚。Git 任务纳入现有取消、退出及重启更新保护。
- 冲突时保留操作工作区，可打开目录手动解决。放弃时点击「中止」；手工提交并确认工作区干净后，点击「完成处理」检查并清理，不自动补推送。不会强制删除有改动的工作区；若合并已经提交或目标已有新提交，「中止」会拒绝自动撤销，需确认后完成处理或自行通过 Git 整理。
- 操作日志保存在应用数据目录 `backend-worktrees/<操作ID>/operation.json`。进入工作台自动读取实际执行过的待处理操作，未确认执行的预检计划不展示为历史操作。执行结果使用中文状态，显示仓库总数、成功、失败和未执行数量及逐仓库说明；有待处理操作时才显示记录选择和刷新入口，记录以仓库名称和状态区分。应用重启后未结束的操作恢复为暂停状态，提供处理入口；已取消但仍保留工作树的记录也会保留处理入口，绝不自动重跑或推送。

旧配置缺少子项目和 SCM 项目关联时默认为空，`schemaVersion` 保持 1；导入导出包含项目元数据及分支映射，不包含 SCM 登录凭据。浏览器预览不访问本机仓库或 SCM，会显示桌面应用提示。真实 SCM 登录、仓库权限、合并和推送需由用户在目标环境验收；自动化测试只使用脱敏 HTML 和临时本地 Git 仓库。

## 环境体检

项目详情右上角提供「环境体检」，按当前项目类型和启用的平台检查目录、所选终端、指定 Node/nvm 版本及每条命令的环境变量语法。uni-app 项目还会检查 HBuilderX 与辅助功能状态；启用 App 构建时检查 manifest、App.vue、平台 AppID、Android 原生工程/模块/Gradle wrapper、JDK 和产物目录。结果分为通过、警告、异常和不适用，并提供重新体检、编辑项目与偏好设置入口。

体检保持只读，不运行项目命令、不启动开发工具、不写入源码，也不自动请求系统授权；只有点击「请求授权」才会触发 macOS 原生提示，授权后点击「重新体检」。终端默认环境的实际 Node 版本、JDK 与 Gradle 的兼容性不能仅凭文件判断，会明确提示待确认，不将目录存在误报为完整环境可用。Windows 继续检查基础项目环境，HBuilderX 自动化及 App 构建相关项标为不适用。

## 构建历史

在 uni-app「App 构建」的「构建配置」标题右侧点击「构建历史」，进入当前项目的独立历史页面，可返回构建配置并保留原先选择的构建目标。历史记录 APK、Android WGT、iOS WGT 的版本、构建时分支、开始时间、耗时、结果摘要和产物路径。任务收尾和 AppID 恢复完成后才记录最终结果；异常退出遗留的执行中记录，下次启动标记为中断。终端或菜单的「已触发」不会被记作构建成功。

- 历史保存在应用数据目录的 `build-history.json`，重启后仍可查看。点击历史页「保留设置」，可配置每个项目保留 1～1000 条已结束记录，默认 100 条；运行中记录不会被裁掉。该设置对所有项目生效，降低上限需二次确认，保存后立即清理各项目最旧的超限记录，仅清理历史元信息、不删除实际产物，并显示移除总数。
- 保留设置与记录一起原子保存；旧版数组格式历史继续按默认 100 条读取，后续写入自动迁移，已有记录不会因格式升级而清空。
- 页面可选择最多显示 10、20、50、100、200、500 或 1000 条记录，默认 20 条，并显示当前展示数和总数。选择保存在本机，跨项目和重新打开页面沿用；调整展示数量不会删除历史，也不改变存储保留上限。
- 展开记录可以查看结果摘要和产物，存在的文件可在文件管理器中定位；已移动或删除的文件明确标记为缺失。
- 「移除记录」经确认后只删除历史条目，不删除源码或实际产物；运行中记录不能移除。
- 历史仅保存构建元信息，不持久化命令、环境变量或完整业务日志；当前执行日志仍在「任务输出」中查看。历史独立于项目配置，不随 JSON 配置备份导出。
- 历史文件损坏或写入失败会明确提示，保留损坏文件，不将历史保存失败误报为实际构建失败。浏览器预览不读取本机构建历史。

## App 构建

在项目的「App 构建」设置中分别填写 Android AppID 和 iOS AppID。这里是 uni-app 的 `__UNI__...`，不是 Android package name 或 iOS Bundle ID。可读取当前 manifest AppID，再手动决定填入哪个平台。

支持：

| 目标        | 依赖                                                                    |
| ----------- | ----------------------------------------------------------------------- |
| Android APK | HBuilderX、Android 离线原生工程、Gradle wrapper、兼容的 JDK/Android SDK |
| Android WGT | HBuilderX、Android AppID                                                |
| iOS WGT     | HBuilderX、iOS AppID                                                    |

APK 采用「HBuilderX 生成本地 App 资源 → 复制资源到原生工程 → Gradle 构建」流程。工程需已完成 Android SDK、签名、DCloud 离线 SDK 等配置。DevDock 不创建或修改签名材料。

- 自动查找根目录或 `src/manifest.json`，也可手动指定。支持注释和数字/字符串 versionCode，修改时保留其他字段与注释。
- 构建面板默认读取 versionName/versionCode，用户输入的新版本写回源码。APK 同步原生模块 Gradle 版本；可选同步 `main.js` 的 `appVersion()`。
- 不自动套用 `3.4.8 → 34800` 等项目专属编码规则。versionCode 为有效的非负整数，并受原生构建版本范围约束。
- AppID 仅在构建时临时切换；成功、失败或取消后恢复原值，保留版本修改，并按构建前的 LF/CRLF 风格写回；原子写入保留原文件权限，不改变文件属性。恢复记录先落盘，崩溃后下次启动继续恢复。发现 AppID 被用户另行修改时保留冲突记录，不强行覆盖。
- JDK 下拉框右侧提供「获取本地版本」，刷新已安装列表后手动选择；刷新不覆盖当前选择，也支持手动指定路径。
- JDK 按项目配置 → 全局配置 → JAVA_HOME → 系统检测兜底，仅设置构建子进程环境；构建日志会显示实际版本和路径。
- JDK 9+ 通过构建进程的 `JAVA_TOOL_OPTIONS` 追加旧版 Android 工具所需的 `--add-opens`，同时传给 Gradle 派生 JVM，保留已有环境选项及工程 `org.gradle.jvmargs` 内存配置。JDK 8 不添加模块参数。Gradle 6.5 / AGP 4.1.1 等旧工程仍建议优先选择原工程已验证的 JDK 8；这些兼容参数不等同于升级工具链。
- Android 模块首版支持单层模块目录，例如 `simpleDemo`；Gradle task 可填 `:simpleDemo:assembleRelease`。Gradle 版本需是唯一的字面量声明；复杂 flavor/变量表达式会明确拒绝，不猜测修改。
- 原生资源更新前备份到 Android 工程的 `.dev-dock-resource-backups`；uni-app 源资源不会被移走。
- WGT 在 `<uniapp项目>/unpackage/release` 直接生成版本文件：Android 为 `3.8.8.wgt`，iOS 为 `3.8.8-ios.wgt`，不创建额外子目录。同平台同版本重新打包会替换对应文件，其他版本与平台的包保留。
- APK 复制到可配置的归档目录，默认 `<uniapp项目>/unpackage/release`，原样保留 Gradle 生成的文件名，不额外添加版本或任务 ID。例如当前原生工程输出 `hyx-版本号-yyyyMMddHHmm.apk`，归档后仍保持该名称；再次产生同名文件时，以本次完整产物替换。同目录归档不会复制覆盖源文件。历史 `dev-dock` 目录及其中产物不会自动删除。

`scripts/build-app.sh` 和 `scripts/build.sh` 从指定的 build-app skill 脚本复制后适配，原始脚本保持不变。执行只依赖本项目随包脚本；项目路径、AppID 和 JDK 均通过配置传入。

## HBuilderX 菜单自动化

在「运行与发行」中添加操作，选择 HBuilderX 菜单方式，用 `/` 分隔层级，例如：

```text
运行 / 钉钉小程序-开发
发行 / 自定义发行 / 钉钉小程序-生产
运行 / 运行到小程序模拟器 / 微信开发者工具
发行 / 小程序-微信
```

点击「读取 package.json uni-app.scripts」，仅从当前配置的项目根目录读取 `package.json` 的 `uni-app.scripts`，不依赖 HBuilderX 当前激活项目，不启动 HBuilderX、不抢焦点，也不需要辅助功能权限。依据 [uni-app 扩展编译配置](https://uniapp.dcloud.net.cn/collocation/package.html) 中的 `title` 和 `env.UNI_PLATFORM` 提供候选；每个脚本均可选择运行或发行，不按 dev/prod 名称猜用途。运行路径为 `运行 / title`，发行路径为 `发行 / 自定义发行 / title`。可以直接添加为操作，自动启用对应的 Web 或小程序分类，已有相同菜单操作不会重复添加；也可为现有操作选择脚本菜单。切换项目目录后会清除旧候选并忽略旧读取结果。

另保留「读取 HBuilderX 菜单」入口，方便选择内置公共菜单。界面明确说明：读取的是 **HBuilderX 当前激活项目的菜单，不一定是正在配置的项目**；目标项目的自定义脚本应通过上方 `package.json` 读取。两种来源各自展示、互不覆盖。HBuilderX 读取保持只读、不主动切换项目；微信内置运行项附带的活动项目名称会转为通用菜单名称，执行时再定位目标项目。

`env.UNI_PLATFORM` 为 `h5` / `web` 的脚本归入 Web，`mp-*` 脚本统一归入小程序，包括微信、支付宝/钉钉、百度、抖音、QQ 等，不再要求钉钉专属标记。其他不属于上述分类的平台会注明暂不支持导入。标准 `package.json.scripts` 仍单独读取为终端命令。自定义菜单最终是否可执行，仍需在 HBuilderX 中打开目标项目并验证；读取文件成功不代表实际编译成功。微信内置预设仍会匹配项目名称并排除「指定页面」菜单。

重复运行时会核对 HBuilderX 实时编译进程所属项目，而不把当前打开的 App.vue 当作运行者。同项目会提示已运行；其他项目占用同名命令时，会显示实际项目名称并说明当前项目未启动。未配置的项目使用真实目录名；归属不明确时会明确提示，不能可靠判断就不停止任务。占用提示同时显示在主窗口和快捷弹框中。

HBuilderX 的运行命令旁提供「停止」按钮，快捷弹框也提供停止图标，例如「钉钉小程序-开发」对应「停止钉钉小程序-开发」。停止前确认实际运行者属于当前项目，跨项目或归属未知时拒绝操作；没有在运行则提示无需停止，不自动停止并切换到另一个项目。终端脚本的进程仍由所选终端管理。

执行前打开目标项目的 `App.vue`，校验前台窗口的项目上下文和菜单可用状态。窗口标题需能识别项目目录名与 App.vue；不同 HBuilderX 版本或自定义显示名称可能需要调整适配。菜单任务串行执行，避免跨项目抢占前台。

用户触发 HBuilderX 构建、HBuilderX 菜单读取/执行或 Ghostty / iTerm 操作时，DevDock 会先检测辅助功能权限；缺少权限时自动打开「系统设置 → 隐私与安全性 → 辅助功能」并暂停操作，构建尚未写入版本或切换 AppID。请手动开启 DevDock 权限，重启应用后重试。若执行过程中仍收到 `-25211`，也会打开设置并显示授权提示；设置打开失败时会提示手动前往。系统对控制 System Events、HBuilderX 或终端的自动化授权仍需按提示允许。

WGT 确认框必须能通过辅助功能识别，具备 WGT 标识、目标项目的输出路径及对应按钮。支持嵌套控件和 `确定(O)` 等 Qt 快捷键后缀；无法唯一识别时明确失败，不盲按回车。

「发行 → 自定义发行 → 项目脚本」点击菜单后，HBuilderX 还会弹出「微信小程序发行」等确认页。DevDock 等待该弹框出现后，优先点击其中可唯一识别的「发行 / 发布 / 打包」按钮；识别不到按钮但确认标题或说明属于发行弹框时，按回车触发默认「发行」按钮。仅当弹框文本明确包含发行类关键词才发送回车，未检测到发行弹框时失败并提示，不在其他弹框上盲按回车。

菜单操作只报告「已触发」，不将点击菜单误报为编译/发行成功。APK/WGT 另行检查本次新产物、版本/AppID（本地资源）、ZIP 完整性和相关进程退出状态。

## 终端

macOS 支持 Terminal、Ghostty、iTerm，Windows 支持 Windows Terminal、PowerShell 及 PowerShell 7，均可手动指定终端路径。项目终端可以覆盖全局选择。

- 项目「运行与发行」中的终端命令使用「项目名 · 执行命令」作为标签标题，不包含目录切换、环境变量或 nvm 激活前缀。打开 AI/全局终端命令或仅打开目录时不主动设置标题。
- Terminal 通过 AppleScript 打开终端执行。
- Ghostty / iTerm 使用前台自动化创建标签页并粘贴命令；需要默认的新标签页快捷键和辅助功能权限。包含大量环境变量的长命令会按 400 字符分块粘贴，块间留出终端处理时间，全部粘贴完成后再回车并恢复剪贴板，避免命令被截断。
- 工作目录安全引用，用户自定义命令按原意执行。终端任务只显示「已触发」，运行日志与服务停止在对应终端中处理。
- 取消 DevDock 构建可以停止它管理的子进程，无法保证撤回 HBuilderX 已开始的内部发行或终端已收到的命令；请在对应工具中确认。

### 执行 npm 命令需要辅助功能权限吗？

`npm run dev` 本身不需要辅助功能权限。通过 DevDock 启动时，权限取决于所选终端的启动方式，与执行 npm、其他命令或仅打开目录无关：

| 系统与终端                                   | 辅助功能权限              | 启动方式                                                                       |
| -------------------------------------------- | ------------------------- | ------------------------------------------------------------------------------ |
| macOS Terminal                               | 不需要                    | 使用原生 AppleScript `do script`；首次可能需要允许 DevDock 自动化控制 Terminal |
| macOS Ghostty / iTerm                        | 需要                      | 通过 System Events 模拟新建标签、粘贴命令与回车                                |
| Windows Terminal / PowerShell / PowerShell 7 | 不涉及 macOS 辅助功能权限 | 直接启动终端进程                                                               |

提示「辅助功能权限不足，已暂停本次操作」时，命令尚未交给终端。继续使用 Ghostty / iTerm，需要在「系统设置 → 隐私与安全性 → 辅助功能」允许 DevDock，重启应用后重试。

如果不希望授予辅助功能权限，可以在「偏好设置 → 终端命令」将默认终端改为 Terminal 并保存，同时检查项目的终端配置：项目单独指定的终端优先于全局设置，需将项目终端改为跟随全局或直接选择 Terminal。macOS 的「自动化」与「辅助功能」是两种独立权限，切换 Terminal 后仍需按系统提示允许自动化控制。

### 打开项目目录并执行命令

所有项目详情（包括后端项目）提供「打开并执行命令」。在「偏好设置 → 终端命令」维护名称、执行内容和启用状态，例如 `claude`、`codex`、`codebuddy`、`git pull`，也支持其他本地命令及参数、带引号的可执行文件路径。快捷添加只提供示例，不自动安装工具或处理登录。

默认终端及其路径在「终端命令」模块配置。点击任一已启用命令右侧的「设为默认」，保存设置后成为全局默认；点击当前「默认命令」按钮可取消，不设默认时不自动执行命令。项目默认跟随全局，也可在项目详情中单独选择专用命令，选择立即保存，仅影响当前项目。项目专用命令已删除或禁用时，不擅自换用其他命令。名称、命令、启用状态、全局默认及项目选择均随 JSON 备份保存；导出包含当前表单草稿。合并导入保留本机全局设置，替换导入应用备份设置。

主窗口的「打开并执行」进入目录后执行可用命令，未选择时提示配置；「仅打开目录」始终只进入目录，保留命令选择。菜单栏快捷弹框在项目折叠箭头右侧提供两个按钮：终端图标仅进入目录，播放图标进入目录并执行项目专用或全局默认命令；无可用命令时只进入目录。快捷执行重新读取已保存偏好，避免使用过期选择。

终端按项目配置 → 全局配置 → Terminal 的顺序选择。此入口使用终端默认环境，不启用项目为 npm 配置的 nvm 版本，也不修改项目原有运行命令。旧版 AI 工具配置继续兼容。日志「已触发」仅表示已交给终端，实际结果、日志及退出在终端查看。

### Node.js 版本

添加或编辑 Node.js 项目时，可以选择该项目使用的 Node.js 版本。「获取本地版本」读取本机 nvm 已安装版本，按版本号排序；也可以选择「跟随终端默认版本」。每个项目可以使用不同版本，选择随项目配置及 JSON 备份保存。

指定版本后，终端先进入项目目录：macOS 通过 nvm 启用指定版本，Windows 将 nvm-windows 选定版本的目录加入本次会话 PATH，再执行所选命令。只有版本启用成功才继续运行；已卸载的版本或失效的 nvm 路径会报错，不自动安装，也不悄悄改用其他版本。切换只作用于新终端会话，不修改 nvm 默认版本或其他终端。

### 环境变量

每条终端命令可在「运行与发行」的编辑区单独填写环境变量，格式为 `KEY=VALUE;KEY2=VALUE2`，也可以用换行分隔，例如：

```text
AI_ALERT_EMAIL_ENABLED=false;ALERT_EMAIL_FROM=示例发件人 <sender@example.com>;ALERT_EMAIL_SMTP_HOST=smtp.qq.com;
```

值支持空格、`<`、`@` 等符号，首尾空白会去除。复杂值（如 JSON）可用单引号或双引号包裹，引号内的分号和换行不会被当作分隔符；双引号内的 `\"` 会还原为 `"`，例如 `AI_CONFIG="[{\"name\":\"weixin\"}]"` 会作为合法 JSON 传入。名称需以字母或下划线开头，重复名称、缺少等号、引号未闭合会拒绝保存并定位到对应命令。执行该命令时在进入目录后、启用 Node 版本前导出，使用单引号安全引用，仅作用于本次终端会话；不同命令可以使用不同变量。环境变量随项目配置和 JSON 备份保存。旧版项目级环境变量会在加载时自动迁移到该项目的终端命令，已单独配置的命令不受影响。

## JSON 备份

偏好设置提供导入/导出 JSON：

- 导出包含 `schemaVersion: 1`、完整项目配置与工具设置，不包含源码、构建产物或 JDK。
- 导入先验证版本、字段、平台、动作及项目唯一性，再选择合并或替换。
- **合并**：按 ID 或目录匹配，更新匹配项目、追加新项目，保留本机工具设置。ID 与目录分别匹配不同项目时拒绝合并，避免误覆盖。
- **替换**：以备份覆盖全部项目及工具设置。替换前可先导出当前配置。
- 导入不会执行命令。路径可能来自其他机器；执行前需确认路径和导入的自定义命令。
- 命令中的敏感值会随配置导出，请妥善保存备份文件。

macOS 配置与恢复记录位于 `~/Library/Application Support/com.devdock.desktop/`。配置写入采用临时文件与原子替换；单实例锁防止另一实例误恢复正在构建的 AppID。

首次升级会从旧版 `com.aidev.desktop` 数据目录复制配置及待恢复记录，保留旧数据，不覆盖已存在的 DevDock 配置。请先退出旧版应用再启动 DevDock，避免两版同时操作同一业务项目。应用标识已更新，macOS 可能需要重新授予自动化和辅助功能权限。旧 JSON 备份仍可导入。

## 公开源码与本地数据

- 文档和测试使用虚构的发件人、项目名称及 `example.com` / `example.invalid` 等示例域名，请勿替换成真实账号或密钥后提交。
- 本机环境变量、应用配置、JSON 备份及签名私钥不属于源码；忽略规则保留 `.env.example` 等模板，模板也只能填写占位值。
- 导出的 JSON 包含完整命令和环境变量，终端截图也可能显示密码或令牌；不要把真实备份、诊断目录或整个工作目录直接上传到公开仓库。
- `.gitignore` 只能防止误加入未跟踪文件，不会清除已经提交的内容。公开仓库前还应检查历史版本与提交作者邮箱；需要时使用 GitHub 提供的 noreply 邮箱。

## 验证边界

仓库测试覆盖配置合并/冲突、备份关系校验、JSONC 字段修改、AppID 恢复及冲突保护、版本字段、产物快照和 package scripts 读取。前端可以在浏览器独立验证。

真实 APK/WGT 发行依赖本机 HBuilderX 版本、辅助功能授权、原生工程和签名环境。语法检查、单元测试和 DevDock 自身打包成功，不代表已替任意业务项目完成真实发行。首次使用建议先用测试项目跑通 WGT，再运行 APK。
